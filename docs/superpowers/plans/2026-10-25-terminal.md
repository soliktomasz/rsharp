# Terminal Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task by task.

**Goal:** Complete Phase 6 with a responsive native terminal, interactive runs and explicit Agent commands.

**Architecture:** `rsharp-core::process` owns PTY spawning and crash cleanup. A gpui-free `rsharp-terminal`
crate owns emulator and bounded asynchronous I/O; the app draws the visible grid and connects its panel
to existing actions, dock, Run controller, configuration dialog and launch steps.

**Tech Stack:** Rust 2024, gpui 0.2.2, alacritty_terminal 0.26, portable-pty 0.9.

**Spec:** `docs/superpowers/specs/2026-10-25-terminal-design.md`

## Global Constraints

- All PTY spawning belongs inside `rsharp_core::process`, under the same Lifeline contract as `spawn`.
- PTY reads, parsing and writes run off the UI thread.
- Pending output and scrollback have explicit bounds.
- Reuse existing fonts, theme tokens, tool-window controls, console links and configuration storage.
- Tests and screenshots get shell history under their own state folder.
- No sessions or workers for an unopened Terminal; no restored processes across restart.
- All shell commands use `rtk`; commits, if made, use message files.

## Review Focus

- Shell job control creates other process groups: foreground and background jobs must end on close/crash.
- Fast process exit must preserve last output and publish its exit exactly once.
- A large paste into a non-reader cannot block the UI or grow pending input without limit.
- Wrapped Unicode selections and links must retain their text and column positions after resize/output.
- A workspace change during startup must not install a session belonging to the old workspace.

### What was verified, and what this machine could not verify

Verified here: `cargo fmt --all --check`; `cargo build --workspace --all-targets`;
`cargo test -p rsharp-core --test pty --test run_terminal`; `cargo test -p rsharp-terminal` (6);
`cargo test -p rsharp-app --test terminal` (8), `--test run` (22), `--test solution_edit` (15),
`--test dock`, `--test actions`, `--test solution_view`, `--test solution_files`, `--test dialogs`; and
`cargo test --workspace --no-fail-fast`: 70 targets pass, and the 6 that fail are the environmental ones
named below.

Not verifiable on this machine, each for a stated environmental reason:

- The real window's capture: `tools/screenshot.sh` finds the window and then fails with "could not create image
  from window", and `screencapture -x` writes an all-black PNG — this terminal has no Screen Recording
  permission. No Terminal window was therefore inspected by eye, and vim, htop and the 10 MB `cat` were not
  exercised by hand; the 10 MB case is a test.
- Every build of a *solution* through dotnet: `dotnet build Shop.slnx` on a two-project fixture hangs past two
  minutes and has to be killed, while the same build with `-m:1` finishes in under a second, and
  `dotnet msbuild` reports "MSBuild server unavailable". This is the machine's MSBuild node IPC, not RSharp.
  It is why `--test build`'s `solution_and_selected_project_operations_…` and both live New Solution tests fail
  here, and why every Roslyn-dependent target fails ("The task was cancelled" from the server's load).
- Windows (ConPTY) and Linux were not run: CI builds and tests all three systems.
- `tools/bench.sh` needs a release build and a window in front for a before/after pair; it was not run, so no
  benchmark claims are made. An unopened Terminal starts no PTY and no thread — `terminal_is_lazy_…` holds that.
